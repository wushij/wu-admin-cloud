# 微服务版页面加载性能优化设计文档

## 1. 文档信息

- **文档名称**：微服务版页面加载性能优化设计
- **适用项目**：`wu-admin-cloud`（前端 `wu-admin-web` + Gateway + BFF + 各业务微服务）
- **对标项目**：`wu-admin-copy`（单体版体验基线）
- **目标读者**：前端、网关、BFF、业务服务、测试、运维
- **状态**：Draft v1

---

## 2. 背景与问题定义

当前微服务版在“首次进入系统、首次进入业务页、刷新页面”时，用户感知到明显的加载转圈，体感慢于单体版。  
已确认问题并非单一接口慢，而是链路叠加导致：

1. **请求跳数增加**：浏览器 -> Vite 代理 -> Gateway -> BFF/服务 -> Feign 下游
2. **前置阻塞较多**：应用挂载前配置加载、路由守卫鉴权串行
3. **页面初始化并发竞争**：Layout 启动即拉消息、配置、字典、WebSocket、监控轮询
4. **聚合接口冷缓存退化**：BFF 扇出调用下游服务，最慢分支决定首屏时间
5. **重复请求/串行请求存在**：同一场景重复拉用户信息，部分接口前后依赖可并行却未并行

---

## 3. 现状链路分析

### 3.1 首屏（登录后进入首页）关键路径

1. `main.ts` 中 `siteStore.loadConfig()` 阻塞 `app.mount`
2. `router.beforeEach` 中 `refreshUserStore()` 阻塞 `next()`
3. `refreshUserStore()` 内部串行：`initSessionKey()` -> `getInfo()`
4. Dashboard 与 Layout 并发触发多类请求，存在连接/CPU 竞争
5. Dashboard `/stats` 命中冷缓存时，BFF 内部触发多路 Feign 聚合

### 3.2 用户感知“转圈”来源

- 列表页普遍 `v-loading` 绑定数据请求
- 路由守卫阻塞期间页面不可交互
- 某些页面存在串行请求链，放大尾延迟

### 3.3 与单体差异本质

- 单体：单进程内聚合 + 本地调用，网络跳数少
- 微服务：鉴权、路由、聚合、服务发现均引入额外延迟

结论：问题是**系统级性能体验问题**，需要前后端与网关协同治理，而非单页面局部修修补补。

---

## 4. 优化目标与范围

## 4.1 目标（SLO）

以开发环境（本机 Nacos + 本机服务）与测试环境分别验收：

1. **首页首屏可见时间（FCP）**：下降 30% 以上
2. **首页数据可用时间（TTI-like）**：下降 40% 以上
3. **关键列表页首包到列表可交互**：下降 30% 以上
4. **路由切换平均耗时**：下降 25% 以上
5. **95 分位慢请求占比**：下降 40% 以上

## 4.2 非目标

1. 不改变现有权限模型与菜单语义
2. 不改业务字段定义、不改前端交互设计
3. 不在本阶段引入重型中间件（如全新消息总线）

---

## 5. 优化设计总览

采用“三层治理、分阶段落地”：

1. **前端启动链路减阻塞**（最快见效）
2. **BFF 聚合与缓存稳定化**（核心收益）
3. **网关与运行时策略分环境调优**（避免开发体验劣化）

---

## 6. 详细方案设计

## 6.1 前端链路优化

### 6.1.1 方案 A：去重用户信息刷新

**问题**：路由守卫已刷新用户态，Dashboard 首次再触发一次刷新。  
**设计**：

1. 在 `userStore` 增加短时效“用户信息刷新中的 Promise 缓存”（in-flight 去重）
2. 对外暴露 `ensureUserReady()`，重复调用复用同一 Promise
3. Dashboard 首次初始化调用 `ensureUserReady()`，不直接二次 `refreshUserStore()`

**收益**：减少一次 `/auth/session-sign-init + /auth/info` 链路。

### 6.1.2 方案 B：`initSessionKey` 与 `getInfo` 解耦

**问题**：当前是强串行，延迟线性叠加。  
**设计**：

1. 登录后优先异步刷新 session key（已有）
2. 首次进入时改为“尽力并行”：  
   - 若本地 key 可用：直接 `getInfo`
   - 若不可用：触发单例 key 获取，但不重复阻塞后续并发请求
3. 保留签名失败自愈重试逻辑，保证安全兜底

**收益**：削减鉴权准备阶段耗时。

### 6.1.3 方案 C：Layout 初始化分层加载

**问题**：页面初始化时后台请求过多并发竞争。  
**设计**：

将 Layout 启动任务拆三层：

1. **P0（阻塞必要）**：主题、最小用户态
2. **P1（首屏后立即）**：消息摘要、站点配置
3. **P2（空闲时）**：字典预热、WebSocket、监控轮询

实现方式：

- `requestIdleCallback`（不支持时 `setTimeout` 兜底）
- 监控轮询仅在进入监控相关路由或显式 admin 场景延迟启动

**收益**：降低首屏并发峰值，减少“列表页和后台任务抢连接”。

### 6.1.4 方案 D：页面级加载体验优化

**问题**：全容器 `v-loading` 导致“页面看起来卡住”。  
**设计**：

1. 列表页改为骨架占位 + 局部 loading
2. 保留头部/筛选区可交互，避免“整页冻结”
3. 异常回退提示统一（超时、网关错误、服务未就绪）

**收益**：提升感知性能，降低用户焦虑。

---

## 6.2 BFF 聚合与缓存优化

### 6.2.1 方案 E：聚合超时策略分级

**问题**：最慢分支拖累整体。  
**设计**：

1. 指标分级：核心指标（用户/访问/权限相关）与次要指标（聊天未读等）
2. 核心指标超时阈值高于次要指标
3. 次要指标超时快速降级，返回默认值并上报埋点

**收益**：确保首屏先可用，再逐步补齐非核心数据。

### 6.2.2 方案 F：缓存策略升级

**设计**：

1. 维持短 TTL（如 30~60s）防止陈旧
2. 增加“异步刷新（stale-while-revalidate）”：
   - 命中旧值先返回
   - 后台异步刷新缓存
3. 避免缓存击穿：对高频 key 增加短暂互斥锁

**收益**：显著降低冷缓存抖动，平滑 P95 延迟。

### 6.2.3 方案 G：可观测性补强

**设计**：

1. BFF 为每个下游调用增加耗时日志与 traceId
2. 记录聚合结果来源（cache-hit/cache-miss/degraded）
3. 输出慢调用榜（按服务、接口、分位数）

**收益**：定位从“猜测”变为“证据驱动”。

---

## 6.3 网关与运行时优化

### 6.3.1 方案 H：开发环境轻量策略

**设计**：

1. dev profile 下可关闭部分重试链路叠加（如前端 + 网关双重重试）
2. dev profile 下可降低加密签名策略强度（仅本机调试）
3. 明确“生产安全策略不降级”，通过 profile 隔离

**收益**：提升本地联调速度，减少“看起来系统慢”误判。

### 6.3.2 方案 I：网关路由与超时基线统一

**设计**：

1. 统一核心接口超时基线，避免“前端超时 > 网关超时 > 服务超时”错配
2. 精简重复 RewritePath 与无效默认过滤链配置
3. 明确 503 处理规范：哪一层重试、重试几次、间隔多少

**收益**：减少重试风暴与超时雪崩。

---

## 7. 实施计划（分期）

## 7.1 Phase 1（1~2 天，前端快赢）

1. 用户态刷新去重（A）
2. Layout 分层加载（C）
3. Dashboard 去重复刷新（A 落地场景）
4. 页面骨架/局部 loading 首批改造（D，用户/角色/首页）

**验收**：首屏 FCP 与列表页首包时间明显下降，且功能不回归。

## 7.2 Phase 2（2~4 天，BFF 稳定化）

1. 聚合指标分级与超时降级（E）
2. stale-while-revalidate 缓存机制（F）
3. 聚合链路可观测日志（G）

**验收**：P95 延迟下降、冷缓存抖动收敛。

## 7.3 Phase 3（1~2 天，网关与策略治理）

1. dev/prod 分环境策略（H）
2. 重试/超时/改写规则收敛（I）

**验收**：开发环境体感与线上稳定性均提升。

## 8. 测试与验收方案

## 8.1 指标采集

1. 前端埋点：FCP、路由切换耗时、接口耗时、页面可交互时间
2. 网关指标：请求总量、503 比例、重试次数、P95/P99
3. BFF 指标：cache-hit 比例、下游分支耗时、降级次数

## 8.2 测试用例

1. 冷启动登录进入首页
2. 首次进入用户/角色/工单列表页
3. 快速切换多菜单页
4. 下游单服务故障/超时场景（验证降级）
5. Nacos 单节点抖动场景（验证重试策略）

## 8.3 成功判定

满足第 4 章 SLO 且无 P0 功能回归。

---

## 9. 风险与回滚

## 9.1 主要风险

1. 异步化后出现状态竞争（用户信息未就绪）
2. 降级返回默认值导致业务误读
3. dev/prod 配置分叉导致行为不一致

## 9.2 控制措施

1. 关键状态加单测与 e2e 校验
2. 降级字段增加“数据来源标记”
3. Profile 配置自动校验与启动时告警

## 9.3 回滚策略

1. 前端特性开关（`FEATURE_BOOTSTRAP_LAYERED_LOAD`）
2. BFF 降级开关（`BFF_DASHBOARD_DEGRADE_ENABLED`）
3. 网关重试与超时参数可热更新回滚

---

## 10. 任务拆分建议（可直接进迭代）

1. **FE-01**：`userStore` 增加 in-flight 去重与 `ensureUserReady`
2. **FE-02**：Dashboard 去除重复刷新路径
3. **FE-03**：Layout 启动任务分层与 idle 调度
4. **FE-04**：用户/角色列表骨架与局部 loading
5. **BFF-01**：Dashboard 聚合指标分级超时策略
6. **BFF-02**：缓存 SWR + 防击穿
7. **BFF-03**：聚合链路埋点与慢调用日志
8. **GW-01**：重试/超时基线治理
9. **OPS-01**：性能看板与压测脚本补齐
