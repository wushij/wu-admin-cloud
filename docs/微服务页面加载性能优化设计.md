# 微服务版页面加载性能优化设计文档

## 1. 文档信息

- **文档名称**：微服务版页面加载性能优化设计
- **适用项目**：`wu-admin-cloud`
  - 实施范围（本期）：PC 前端 `wu-admin-web` + Gateway + Auth + BFF（`wu-admin`）+ 相关业务服务（system / ticket / message 等首屏相关路径）
  - 对齐说明：移动端 `wu-admin-uniapp` 已有 `ensureUserLoaded` 去重，本期不改功能，仅作行为参考
- **对标项目**：`wu-admin-copy`（单体版体验基线，**不在本仓库内**，仅作体感对照）
- **目标读者**：前端、网关、Auth、BFF、业务服务、测试、运维
- **状态**：Draft v2.1（全模块源码复核：修正措辞精度并补强遗漏）

---

## 2. 背景与问题定义

当前微服务版在“首次进入系统、首次进入业务页、刷新页面”时，用户感知到明显的加载转圈，体感慢于单体版。  
已确认问题并非单一接口慢，而是**链路叠加**导致：

1. **请求跳数增加**：开发环境为 `浏览器 → Vite 代理 → Gateway → 服务`；生产为 `浏览器 → Nginx → Gateway → 服务`。其中 **Auth / BFF 等跨服务路径**才会再经 Feign 调下游；普通 `/api/system/**` 等业务请求无 Feign。首屏**阻塞路径不经 BFF**。
2. **前置阻塞较多**：`app.mount` 前 `GET /auth/config`；路由守卫串行 `session-sign-init → /auth/info`。
3. **Auth 后端串行热点（易被忽略）**：`/auth/config` 每次主动刷新多组配置（串行 Feign）；`/auth/info` 用户与菜单串行 Feign。
4. **页面初始化并发竞争**：Layout 挂载后并发拉消息、站点配置、字典、WebSocket、监控轮询（多为 fire-and-forget，主要争连接/CPU）。
5. **Dashboard 冷缓存抖动**：BFF `/admin/dashboard/stats` 未命中 Redis 时多路 Feign 扇出，影响**首页数据可用时间**（非 mount 阻塞）。
6. **重复请求**：守卫已拉用户态后，Dashboard 首次再触发一次 `refreshUserStore()`（已与 `initDashboard` **并行**，不串行拖卡片，但仍多打一轮 Auth，争连接/放大 Auth 负载；浏览器侧菜单/权限/用户本是同一次 `/auth/info`）。

## 3. 现状链路分析

### 3.1 两段链路（必须区分）

| 阶段 | 是否阻塞交互 | 主要路径 | 说明 |
|------|--------------|----------|------|
| **阻塞链** | 是 | Auth（+ System Feign） | 决定白屏 / 守卫转圈 / FCP |
| **后置链** | 否（争资源） | Layout 并发 + Dashboard BFF | 决定首页卡片/消息/字典何时齐 |

```text
[阻塞链]
Browser
  → GET  /api/auth/config              # main.ts await，阻塞 mount
       → Auth.refreshPublicGroups()    # 串行 Feign ×7 配置组 → System；组装时 isCaptchaEnabled 再 loadGroup(login) 常为 ×8（优化后：缓存命中跳过 / 未齐并行）
  → POST /api/auth/session-sign-init   # 守卫 getUserInfo 内 await
  → GET  /api/auth/info                # 守卫 await
       → Feign getUserInfoByUsername   # 含 roles/permissions
       → Feign getMenusByUserId        # 串行，未并行；System 侧现拉全表菜单

[后置链 · Layout onMounted，多数不 await]
  → loadMessages：ticket 通知列表 + message 公告分页 + /message/summary（跨 ticket/message）
  → GET /system/config-group/site
  → GET /system/dict/data/batch
  → WebSocket；监控后台轮询（非 admin 已跳过）

[后置链 · Dashboard]
  →（重复，与 initDashboard 并行）refreshUserStore → session-sign-init + /auth/info
  → GET /api/admin/dashboard/stats     # BFF：Redis 60s 或并行 Feign
  → GET /api/admin/dashboard/recent-logins
  → recordVisit（不阻塞）
```

### 3.2 首屏关键路径（代码级）

1. [`wu-admin-web/src/main.ts`](../wu-admin-web/src/main.ts)：`await siteStore.loadConfig()` 后才 `app.mount`
2. [`router/index.ts`](../wu-admin-web/src/router/index.ts)：`beforeEach` 中无用户或无菜单时 `await refreshUserStore()`
3. [`store/user.ts`](../wu-admin-web/src/store/user.ts)：`getUserInfo` 内 **强串行** `initSessionKey()` → `getInfo()`
4. [`useLayoutBootstrap.ts`](../wu-admin-web/src/views/layout/composables/useLayoutBootstrap.ts)：menus 为空时兜底 `getUserInfo`；随后并发消息/站点/字典/WS/监控
5. [`dashboard/index.vue`](../wu-admin-web/src/views/dashboard/index.vue)：首次再 `refreshUserStore()`（与守卫重复；已与 `initDashboard` 并行）
6. Dashboard `/stats` 冷缓存：BFF 多路 Feign（已有单路 800ms / 整体 1200ms 超时降级）

### 3.3 Auth 后端热点（相对 Draft v1 的补充）

**`GET /auth/config`**（[`AuthConfigLoader.refreshPublicGroups`](../wu-cloud-auth/src/main/java/com/wu/cloud/auth/config/AuthConfigLoader.java)）：

- 每次公开配置接口会串行 `loadGroup`：login / site / register / security / ai / sms / email
- 前端 mount 前 await，是冷启动 FCP 的重要前置成本（常大于 BFF）
- Auth Feign 默认 `read-timeout: 10000`（远大于 BFF 单路 800ms）；下游抖动时串行 7 组会把 FCP 拉得很长

**`GET /auth/info`**（[`AuthServiceImpl.getUserInfo`](../wu-cloud-auth/src/main/java/com/wu/cloud/auth/service/impl/AuthServiceImpl.java)）：

- 浏览器一次请求已聚合：user + roles + permissions + menus
- 服务内侧用户与菜单 **串行 Feign**；菜单无 Redis 读缓存
- System [`InnerUserController.getMenusByUserId`](../wu-cloud-service/wu-service-system/src/main/java/com/wu/cloud/system/controller/InnerUserController.java) 现调用 `menuService.getMenuList()` **拉全表菜单**，`userId` 未用于过滤（与单体「全量可见菜单 + 前端再筛」语义一致，但 DB 成本偏重）
- 边缘路径：session 中 username 缺失时可能 `getUserById` → 再 `getUserInfoByUsername` → 再 menus（最多三次 Feign + 菜单）

**会话签名**：

- [`security-config.ts`](../wu-admin-web/src/utils/security-config.ts) 已对 `session-sign-init` 做 in-flight Promise 去重
- 仍被 `getUserInfo` 强制 await，与 `getInfo` 线性叠加

### 3.4 用户感知“转圈”来源

- 列表页普遍 `v-loading` 绑定数据请求（整表/整卡冻结感）
- 路由守卫阻塞期间页面不可交互
- Auth 配置 / info 串行放大尾延迟
- Dashboard 冷缓存或重复用户刷新放大 Auth 负载与连接争用（卡片等待主要仍看 BFF）

### 3.5 与单体差异本质

- 单体：单进程内聚合 + 本地调用，网络跳数少
- 微服务：鉴权、路由、跨服务 Feign、可选 BFF 聚合均引入额外延迟

**边界说明（避免误判）**：PC 端路由已 `import()` 懒加载、构建侧有 gzip、Layout `keep-alive`（含 Dashboard 常驻缓存）均已存在。本期慢的主因是**鉴权/聚合微服务链路**，不是「缺 code-splitting / 缺 keep-alive」。

结论：问题是**系统级性能体验问题**，需前端 + Auth + System（菜单读路径）+ BFF + 网关协同治理。

### 3.6 已有优化基线（勿重复当“从零建设”）

| 能力 | 现状 |
|------|------|
| session-sign in-flight 去重 | 前端已有 |
| site `loadConfig` | 有 `configLoaded` 短路；in-flight Promise 去重**不完整**（并发两次 `loadConfig` 可能双发；实践上 main await 后再 mount，守卫走 `ensureConfigLoaded`，通常不双发） |
| 字典 batch + 前端内存 Map | 已有；服务端 Redis 多为淘汰脚手架，非读穿透 |
| Dashboard 统计/最近登录并行 | 前端已有；BFF 已填 job 则不再打 overview |
| BFF 并行 Feign + 800ms/1200ms 降级 + Redis TTL 60s | **已有**；缺 SWR、防击穿、核心/次要差异超时；冷缓存时 BFF 仍 Feign job，前端仅在 job 计数>0 时跳过二次 overview |
| 监控后台轮询 | 非 admin 已跳过（`startMonitorBackground`） |
| UniApp `ensureUserLoaded` | 已有；Web 缺失对等 API |

## 4. 优化目标与范围

### 4.1 目标（SLO）

以开发环境（本机 Nacos + 本机服务）与测试环境分别验收；**先采基线再比降幅**：

1. **首页首屏可见时间（FCP）**：相对基线下降 30% 以上
2. **首页数据可用时间（TTI-like，统计卡片可用）**：下降 40% 以上
3. **关键列表页首包到列表可交互**：下降 30% 以上
4. **路由切换平均耗时**：下降 25% 以上
5. **95 分位慢请求占比**：下降 40% 以上

**基线采集约定（本期最低要求）**：

- 工具：浏览器 Performance / Lighthouse（或自建路由+接口耗时埋点）
- 样本：冷启动（清缓存+硬刷新）与热缓存各 ≥ 5 次，取中位数
- 标注环境：dev（含 Vite 代理）与 test（Nginx）分开记，不可混比
- 记录关键接口：`/auth/config`、`session-sign-init`、`/auth/info`、`/admin/dashboard/stats` 的 P50/P95

### 4.2 非目标

1. 不改变现有权限模型与菜单语义（含「全量菜单 + 前端再筛」语义，除非单独做 SYS-01 并验收对齐）
2. 不改业务字段定义；骨架屏仅改加载呈现，不改交互流程
3. 不在本阶段引入重型中间件（如全新消息总线）
4. 本期不改造 UniApp 功能（仅对齐设计说明）
5. 不以「补前端打包拆分 / keep-alive」作为本期主优化项（基线已具备）

### 4.3 范围边界

- **阻塞链优化**：`wu-admin-web` + `wu-cloud-auth`（+ system 内配置/用户/菜单读路径）
- **后置链优化**：Layout / Dashboard 前端调度 + `wu-admin` BFF
- **运行时**：`wu-cloud-gateway` 重试/超时与前端 `retry503` 对齐
- pay / order / ai 等不在首屏关键路径，本期不纳入

---

## 5. 优化设计总览

按**真实收益**排序（与分期落地配合）：

1. **前端去重 + Auth 阻塞链减串行**（最快见效，直接影响 FCP）
2. **Layout 分层 + 感知加载**（降并发峰值与焦虑）
3. **BFF 在已有基线上增强**（SWR / 防击穿 / 分级超时 / 可观测）
4. **网关与分环境策略**（避免重试风暴，改善本地误判）
5. **（可选）System 菜单读路径减负**（SYS-01；与 AUTH-02 互补，不替代 Feign 并行）

---

## 6. 详细方案设计

### 6.1 前端链路优化

#### 6.1.1 方案 A：去重用户信息刷新

**问题**：路由守卫已刷新用户态，Dashboard 首次再触发一次刷新（虽已与卡片数据并行，仍多一轮 Auth）。  
**设计**：

1. 在 `userStore` 增加短时效 in-flight Promise 缓存（对齐 UniApp `ensureUserLoaded`）
2. 对外暴露 `ensureUserReady()`，重复调用复用同一 Promise
3. Dashboard 首次初始化调用 `ensureUserReady()`（或直接依赖守卫结果），禁止无条件二次 `refreshUserStore()`

**收益**：减少一轮 `session-sign-init + /auth/info`（减 Auth 负载与连接争用，而非「解除对卡片的串行等待」——该串行等待现网已消除）。

#### 6.1.2 方案 B：`initSessionKey` 与 `getInfo` 解耦

**问题**：`getUserInfo` 强串行 await key；签名开关开启时拦截器也可能等 key。  
**已有**：`requestSessionSignKey` Promise 单例去重。  
**设计**：

1. 内存已有 key：跳过 await，直接 `getInfo`
2. 无 key：触发单例获取；在签名未强制阻断的路径上尽量与首包并行
3. 保留签名失败自愈重试（`request.ts` 现有逻辑）

**收益**：削减鉴权准备阶段线性叠加（在安全约束内尽力并行）。

#### 6.1.3 方案 C：Layout 初始化分层加载

**问题**：挂载后后台请求并发争连接。  
**设计**：

1. **P0（必要）**：主题、最小用户态（menus 已有则不再拉）
2. **P1（首屏后立即）**：消息摘要、站点配置（消息链跨 ticket 通知 + message 公告 + summary）
3. **P2（空闲时）**：字典预热、WebSocket、监控轮询

实现：`requestIdleCallback`（不支持则 `setTimeout`）；监控轮询在现有「非 admin 已跳过」之上，进一步改为仅在进入监控相关路由或显式需要时启动。

**收益**：降低首屏并发峰值。

#### 6.1.4 方案 D：页面级加载体验优化

**问题**：全容器 `v-loading` 导致“页面卡住”感。  
**设计**：列表页骨架 + 局部 loading；保留筛选区可交互；统一超时/网关/服务未就绪提示。  

**收益**：感知性能（不降低真实耗时，可与 A/C 并行）。

---

### 6.2 Auth 阻塞链优化（相对 Draft v1 新增）

#### 6.2.1 方案 J：`/auth/config` 刷新策略

**问题**：每次公开配置请求串行 Feign 多组配置，阻塞 mount；Auth Feign 读超时 10s 放大尾延迟。  
**设计**：

1. 内存缓存未过期时：**跳过** `refreshPublicGroups` 全量串行，直接组装 VO
2. 需要强一致时（后台刚改配置）：保留主动刷新入口；可改为**并行** `loadGroup`
3. 公开配置路径考虑**更短 Feign 超时** + 单组失败用已有内存缓存兜底（与方案 I 对齐文档化）
4. 前端：评估非登录页是否必须 await 全量 config 再 mount（可先渲染再补齐非关键字段，需评估 `disableDevtool` 等开关）

**收益**：显著压缩冷启动阻塞链（优先级高于纯 BFF 优化）。

#### 6.2.2 方案 K：`/auth/info` Feign 并行

**问题**：用户信息与菜单串行 Feign。  
**设计**：`getUserInfoByUsername` 与 `getMenusByUserId` 并行（用户失败仍失败；菜单失败可空列表降级，与现逻辑一致）。  

**收益**：缩短守卫 `await refreshUserStore` 时间。  
**边界**：只消除 Auth 侧串行等待；System 全量菜单 DB 成本仍在，需 SYS-01 另议。

#### 6.2.3 方案 L（可选）：System 菜单读路径减负（SYS-01）

**问题**：`getMenusByUserId` 名含 userId，实现却 `getMenuList()` 全表；并行 Feign 后单路菜单耗时仍可能偏高。  
**设计**（二选一或组合，须保持与前端再筛语义一致或同步改前端）：

1. 按用户/角色过滤后返回可见菜单；或
2. 全量菜单短 TTL 缓存（进程内 / Redis），变更时主动失效

**收益**：降低 `/auth/info` 菜单分支尾延迟；与 AUTH-02 **互补**，不互相替代。

---

### 6.3 BFF 聚合与缓存优化

#### 6.3.1 方案 E：聚合超时策略分级（在已有基线上增强）

**已有基线**：各分支统一 `RPC_TIMEOUT_MS=800`、整体 `AGGREGATE_WAIT_MS=1200`、失败降级默认值。  
**待增强**：

1. 核心指标（系统统计/访问等）超时可略高于次要指标（IM 未读、文件数等）
2. 次要指标更快降级，并上报埋点
3. 可选：次要指标超时后由前端二次懒补，不挡首屏卡片

#### 6.3.2 方案 F：缓存策略升级（在已有 TTL 上增强）

**已有基线**：Redis key `dashboard:bff:stats:v1:{userId}`，TTL 60s；命中直接返回。  
**待增强**：

1. stale-while-revalidate：TTL 内可返回；临近过期或过期后先返旧值再异步刷新
2. 防击穿：同 key 短暂互斥，避免冷缓存风暴

#### 6.3.3 方案 G：可观测性补强

1. 每下游调用耗时 + traceId
2. 结果来源：`cache-hit` / `cache-miss` / `degraded` / `swr-stale`
3. 慢调用榜（服务、接口、分位数）

---

### 6.4 网关与运行时优化

#### 6.4.1 方案 H：开发环境轻量策略

1. 理清双重重试位点：网关默认 GET `Retry.retries=2`；前端部分接口 `retry503`（如 message bootstrap、dashboard）
2. dev profile 可关闭或降低其中一层重试，避免本地 503 被放大成“系统很慢”
3. 生产安全策略（签名/加密）**不降级**；dev 若调整签名强度须 profile 隔离并文档标明

#### 6.4.2 方案 I：超时与 503 规范

1. 统一基线并文档化：避免「前端 15s / 网关 15s / Auth Feign 10s / BFF 单路 800ms」错配无说明；公开配置路径宜短超时 + 缓存兜底
2. 明确 503：哪一层重试、几次、间隔；Dashboard/消息等只保留一层静默重试
3. 精简无效 Rewrite / 默认过滤链噪音（不影响路由语义前提下）

## 7. 实施计划（分期）

### 7.1 Phase 1（1~2 天，阻塞链快赢）

1. 用户态刷新去重（A）+ Dashboard 去掉重复刷新
2. Auth：`/auth/config` 刷新策略（J，含公开配置短超时/缓存兜底）
3. Auth：`/auth/info` Feign 并行（K）
4. Layout 分层加载（C）
5. （可选并行）骨架/局部 loading 首批（D：用户/角色/首页）
6. （可选）SYS-01 菜单过滤或短 TTL 缓存（L）

**验收**：冷启动 FCP 与守卫等待明显下降；`/auth/config`、`/auth/info` P50 下降；功能不回归。

### 7.2 Phase 2（2~4 天，BFF 增强）

1. 核心/次要超时分级（E）
2. SWR + 防击穿（F）
3. 聚合可观测（G）

**验收**：Dashboard 冷/热缓存 P95 收敛；cache-hit 与 degrade 可观测。

### 7.3 Phase 3（1~2 天，网关与策略）

1. dev/prod 重试与签名策略隔离（H）
2. 超时/503 规范收敛（I）

**验收**：开发环境误判减少；无重试风暴；生产安全策略不变。

## 8. 测试与验收方案

### 8.1 指标采集

1. 前端：FCP、路由切换耗时、关键接口耗时、首页卡片可交互时间
2. 网关：请求量、503 比例、重试次数、P95/P99
3. Auth：`/auth/config`、`/auth/info` 耗时与 Feign 分支耗时
4. BFF：cache-hit 比例、下游分支耗时、降级次数、SWR 次数

### 8.2 测试用例

1. 冷启动登录进入首页
2. 硬刷新（已登录 Cookie/会话仍有效）
3. 首次进入用户/角色/工单列表页
4. 快速切换多菜单页
5. 下游单服务故障/超时（验证 BFF/Auth 降级语义）
6. Nacos 抖动下重试是否叠加（验证 H/I）
7. （若做 SYS-01）菜单变更后可见性与缓存失效是否正确

### 8.3 成功判定

满足第 4 章 SLO（相对**同环境基线**）且无 P0 功能回归。

## 9. 风险与回滚

### 9.1 主要风险

1. 异步化后用户信息未就绪导致权限误判
2. 降级默认值被业务误读为真实零值
3. `/auth/config` 减少刷新导致配置变更延迟感知
4. dev/prod 配置分叉导致行为不一致
5. SYS-01 改变菜单过滤语义时前端侧栏/权限校验不一致

### 9.2 控制措施

1. 关键状态单测 + 守卫/e2e：未登录、无菜单、权限页
2. 降级与缓存响应增加数据来源标记（日志或响应扩展字段）
3. 配置变更：管理端保存后主动失效 Auth 内存缓存 / 调用刷新接口
4. Profile 启动校验与告警
5. SYS-01：菜单 CRUD 后主动失效缓存；与前端筛选行为对齐的回归用例

### 9.3 回滚策略（拟引入，当前代码尚无这些开关）

1. 前端拟引入：`FEATURE_BOOTSTRAP_LAYERED_LOAD`（Layout 分层）
2. BFF 拟引入：`BFF_DASHBOARD_SWR_ENABLED` / 分级超时开关（在现有降级基线上可关增强项）
3. Auth 拟引入：配置“跳过主动全量刷新”开关，异常时回退到现网 `refreshPublicGroups`
4. 网关重试与超时参数可配置回滚（Nacos/本地 YAML）
5. SYS-01：特性开关回退全表菜单查询

## 10. 任务拆分建议（可直接进迭代）

按收益排序：

1. **FE-01**：`userStore` in-flight 去重与 `ensureUserReady`（对齐 UniApp `ensureUserLoaded`）
2. **FE-02**：Dashboard 去除重复 `refreshUserStore`（减 Auth 负载与连接争用）
3. **AUTH-01**：`/auth/config` 缓存命中跳过全量串行刷新；必要时并行 `loadGroup`；公开配置短超时 + 缓存兜底
4. **AUTH-02**：`/auth/info` 用户与菜单 Feign 并行（只消串行等待；菜单 DB 成本见 SYS-01）
5. **SYS-01**（可选）：菜单按用户/角色过滤或短 TTL 缓存；与 AUTH-02 **互补**，须对齐「前端再筛」语义
6. **FE-03**：Layout 启动任务分层与 idle 调度（监控在 admin 门禁之上再按路由启动）
7. **FE-04**：用户/角色列表骨架与局部 loading
8. **FE-05**（可选）：session key 与 `getInfo` 在安全约束下尽力解耦（方案 B）
9. **BFF-01**：核心/次要超时分级（基于现有 800/1200）
10. **BFF-02**：SWR + 防击穿
11. **BFF-03**：聚合埋点与慢调用日志
12. **GW-01**：重试/超时/503 基线治理（对齐前端 `retry503`，文档化 Auth Feign 10s vs BFF 800ms）
13. **OPS-01**：基线采集脚本 + 性能看板
